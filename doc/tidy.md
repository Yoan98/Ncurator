# 文档、测试与代码 Tidy 流程

## 1. 流程

按节点推进，先完成一个节点的审核，给用户审批清理方案，执行完后才能进入下一个节点

- 代码允许重构，但前后功能必须一致：输入输出、校验规则、状态流转、副作用和异常处理不变。死代码、兼容残留须确认无静态或动态消费方后删除。
- 禁止修改提示词及其生成源，包括 prompt 文案、ToolSpec、schema（字段、约束、description / describe）、模板与生成 / 渲染代码；“等价优化”也不能作为修改这些内容的理由。
- 发现需求、实现或测试不一致时，只报告问题，修复单独处理；不得为测试或静态检查通过修改业务行为、放宽断言。
- 修改代码后必须执行并通过相关测试，确认功能等价后才能完成本节点。
- 不得改写已发布 SQLite migration 锁清单内的历史 migration。

## 2. 审阅清单

### 2.1 文档 ↔ 实现对齐

核对文档当前代码实现是否一致。

- [ ] `AGENTS.md` 指向的路径 / 模块仍存在，且职责描述未明显过时。
- [ ] doc一级下的文档 与实现主链路一致。
- [ ] PRD 文档与实际代码是否对齐。
- [ ] ai-harness 文档与实际代码是否对齐。
- [ ] test-plan 文档与实际代码是否对齐。

### 2.2 文档健康

**清理标准**：

- [ ] 临时句、过期备注、半截迁移残留、无消费方的重复段落。
- [ ] 同一事实多处拷贝且已漂移 → 收敛到单一真相源。
- [ ] 无价值，无意义的语句。
- [ ] 标题与内容不符的。
- [ ] 先阅读 [`doc/doc-guidelines.md`](doc-guidelines.md)，按各文档的职责、骨架和编写要求逐章检查，对越界、混杂、重复及结构不符的内容提出整理方案。

**重构触发**：

- [ ] 一章膨胀到难以按产品域或主题扫完；或补丁堆到「补丁 > 结构」。

### 2.3 PRD ↔ 测试计划对齐

核对prd文档的每项功能与对应测试计划，对应测试代码是否对齐，如prd的workbench的每个功能点是要对应上test-plan下的workbench的每个测试点的。

- [ ] Settings
- [ ] Workbench
- [ ] AI 产品相关验收若落在 PRD，同样核对；

### 2.4 测试分层与清理

- [ ] 测试分层是否符合 `doc/test.md`文档与对应test-plan下测试文档的设计。
- [ ] 重复或者无意义，无价值的测试case。

### 2.5 代码整洁

| 工具 | 用途 |
|------|------|
| `pnpm knip` | 失效文件、错误 import、未使用依赖（`knip.json`） |
| `tsc --noEmit` / eslint | 未使用局部量、未使用 import |

- [ ] 失效文件、错误相对路径 import。
- [ ] 死常量 / `@deprecated` 别名 / 无消费方的重复 export。
- [ ] 历史兼容分支、fallback：确认无消费方后删除。
- [ ] 消除重复与合理抽象。
- [ ] 简化复杂实现。
- [ ] 优化文件与代码组织。
- [ ] 类型禁止使用非必要的 `any` 与 `unknown`。
- [ ] 字段遵循最小必要原则。
