# 文档、测试与代码 Tidy 流程

本文件定义周期性整理流程与固定审阅清单。Tidy **不**自动改仓库：先按清单审计 → 汇总计划 → 等用户决策 → 再执行。未获批前不删除、合并或改写文档、测试与代码。

## 1. 流程

1. 按 §2 固定审阅清单逐项勾选审计（可并行，但每项必须有结论）。
2. 产出「Tidy 计划」：建议删 / 并 / 改 / 补，以及必须由用户拍板的问题。
3. 用户勾选批准范围后，只执行获批项。
4. 执行后如改了 PRD / 测试计划 / 代码边界，同步相关入口（`AGENTS.md`、对应 `doc/test-plan/**`）。

允许破坏性清理（死代码、错误兼容残留），但不得改写已发布 SQLite migration 锁清单内的历史 migration。

## 2. 固定审阅清单

每次 Tidy 都必须过完下列检查；无关项写「不适用」并简述原因。

### 2.1 文档

- [ ] `AGENTS.md` 文档入口与 `doc/**` 实际文件一致（含新增/生成物是否应登记）。
- [ ] 架构 / database / release / ui-style / harness 与实现目录、主链路一致。
- [ ] **边界**：PRD 只写用户可见行为与验收；工具协议、graph、prompt、schema 细节归 `doc/ai-harness/**` + `doc/test-plan/ai-test.md` + 代码，不在 PRD 重复。
- [ ] 文档之间无互相矛盾或大段复制。
- [ ] 历史噪音、过期描述、错误编号（重复 AC、错绑 AC）已标出。
- [ ] 生成文档（如 `doc/ai-tool-prompt-audit.md`）的治理方式明确：入库 / 按需生成 / 缩成索引。

### 2.2 PRD ↔ 测试计划 ↔ case

- [ ] 各 PRD 验收编号在对应 `doc/test-plan/**` 有归属，或明确标为手动 / 发布前检查 / 由其他域承担。
- [ ] 测试计划 Oracle 引用的 AC 与 PRD 语义一致（无错绑）。
- [ ] 计划中的 `caseId` 能在 `tests/case/**` 被 runner 发现；一文件多 case 时计划写明文件归属。
- [ ] 分层未被破坏：Workbench E2E 不重复枚举工具内部算法；AI tool / mock / live / unit 职责符合 `doc/test.md` 与 `ai-test.md` §3.4。
- [ ] 多余 / 等价 Oracle 重复 / 覆盖缺口分别给出删、并、补建议（补测须先确认分类：AI / Settings / Workbench / Unit）。

### 2.3 Settings / Workbench（含定时任务）链路

对每个产品域核对：

`PRD 功能点 → test-plan case → tests/case 文件`

- [ ] Settings：`SET-*` 链路完整。
- [ ] Workbench：`WB-*` 链路完整。
- [ ] 定时任务：`ST-*` 链路完整（PRD 在 `doc/prd/scheduled-task.md`）。
- [ ] 跨域交叉点（如未绑目录、帮助入口、标题栏）无双边重复硬断言；或明确「只在一侧断言 UI 文案」。

### 2.4 测试用例

- [ ] 输入、主行为、Oracle 均等价的 case / it：建议删或并。
- [ ] 「看起来重复但分层不同」的保留并写明理由（tool / mock / live / e2e）。
- [ ] live 成本重叠（同族场景多条真实模型）是否仍需独立：列出供决策，默认不擅自砍。
- [ ] Unit 是否已被 AI tool 契约完全覆盖：等价则建议删 Unit 重叠 it。

### 2.5 代码整洁度

用工具辅助，**人工确认后再删**：

| 工具 | 用途 |
|------|------|
| `pnpm knip` | 失效文件、错误 import、未使用依赖（配置见 `knip.json`） |
| `tsc --noEmit` / eslint | 未使用局部量、未使用 import |

检查项：

- [ ] 失效文件、错误相对路径 import。
- [ ] 死常量 / `@deprecated` 别名 / 纯重复 export（确认无消费方）。
- [ ] 历史兼容分支、fallback：无消费方则删除（AGENTS 允许破坏性重构）。
- [ ] 过度复杂或重复实现：能更简单则建议替换。
- [ ] **禁止**按 knip「Unused exports / Unused exported types」批量删除（大量为同文件内部使用或 schema 类型双份）。

### 2.6 输出物（计划必含）

- 建议执行项（删 / 并 / 改 / 补），尽量落到文件或 caseId。
- 需用户决策的问题（默认建议可一并给出）。
- 明确不在本次范围的项。
- 若工作区已有未提交相关改动：注明避免冲突的策略。

## 3. 代码清理类别（审计时归类用）

### 3.1 死代码

不可达分支、未使用导出（全仓无引用）、无入口失效文件。

### 3.2 历史兼容残留

旧格式别名、迁移守卫、仅为旧版本保留的 fallback；确认无消费方后删除。

### 3.3 无用代码

未使用 import / 局部变量 / 依赖 / 脚本 / 资源。

### 3.4 简洁性

过度复杂实现简化、合理去重、去掉无用抽象、可选+兜底改为必填、文件职责整理。
