# 文档、测试与代码 Tidy 流程

周期性整理：先审计 → 出计划 → 用户批准 → 再改仓库。未获批前不删除、合并或改写文档、测试与代码。

## 1. 流程

1. 按第 3 节清单逐项审计（可并行；每项必须有结论，无关则写「不适用」）。
2. 产出「Tidy 计划」：删 / 并 / 改 / 补，以及需拍板的问题。
3. 只执行获批项。
4. 若改了 PRD / 测试计划 / 代码边界，同步 `AGENTS.md` 与对应 `doc/test-plan/**`。

允许破坏性清理（死代码、兼容残留），但不得改写已发布 SQLite migration 锁清单内的历史 migration。

文内互指用「第 N 节」或章节标题，不用 `§`。

## 2. 文档职责

| 类型 | 写什么 | 不写什么 |
|------|--------|----------|
| PRD（`doc/prd/**`） | 产品功能、场景、交互结果、验收口径 | 实现细节：工具协议、schema、graph、prompt、内部 ID |
| 架构 / database / release / ui-style | 模块关系、存储、发版、视觉规范 | 产品验收编号清单 |
| AI harness（`doc/ai-harness/**`） | 消息、投影、compaction、工具契约 | 产品功能说明书式的用户故事 |
| test-plan | 回归范围、case 设计、Oracle 归属 | 替代 PRD 定义产品目标 |
| 生成物（如 `ai-tool-prompt-audit.md`） | 契约快照 / 活例子 | 手写长期真相源（改工具时对照即可） |

定时任务产品规格在 `doc/prd/scheduled-task.md`，归属 Workbench 产品域（入口与会话侧消费）；审计时并入 Workbench 链路，不单开一域。

## 3. 审阅清单

每项只出现一次。

### 3.1 文档健康

- [ ] `AGENTS.md` 入口与 `doc/**` 实际文件一致（含生成物是否登记）。
- [ ] 架构 / database / release / ui-style / harness 与实现、主链路一致。
- [ ] **清理**：迭代堆积的临时句、过期备注、半截迁移残留、重复表述、错误或错绑编号。
- [ ] **审视重构**：文件是否该拆 / 并 / 重写某章；只写入计划，批准后再做。
- [ ] 文档之间无互相矛盾；大段复制能收敛到单一真相源则建议收敛。
- [ ] 生成文档治理明确：入库 / 按需生成 / 缩成索引。

### 3.2 覆盖链路

一次核对：`PRD 功能 / AC → test-plan case → tests/case`。

按产品域勾选（定时任务并入 Workbench）：

- [ ] Settings（`SET-*`）
- [ ] Workbench（`WB-*`，含 `ST-*`）
- [ ] AI 产品相关验收若落在 PRD，同样走通；纯工具协议则归 harness + `ai-test`，不要求塞进产品 PRD

顺带检查：

- [ ] 每个 AC 在计划中有归属，或标明手动 / 发布前检查 / 由其他域承担。
- [ ] 计划 Oracle 引用的 AC 与 PRD 语义一致（无错绑）。
- [ ] `caseId` 能被 runner 发现；一文件多 case 时计划写明文件归属。
- [ ] 跨域交叉点（未绑目录、帮助入口等）无双边重复硬断言，或写明「只在一侧断言」。

### 3.3 测试分层与去重

- [ ] 分层符合 `doc/test.md` 与 `ai-test.md` 第 3.4 节：Workbench E2E 不重复工具内部算法；tool / mock / live / unit 职责清晰。
- [ ] 输入、主行为、Oracle 均等价的 case / it：建议删或并。
- [ ] 分层不同、看起来像重复的：保留并写明理由。
- [ ] live 成本重叠：列出供决策，默认不擅自砍。
- [ ] Unit 已被 AI tool 契约完全覆盖的重叠 it：建议删。
- [ ] 覆盖缺口：补测前先确认分类（AI / Settings / Workbench / Unit）。

### 3.4 代码整洁

工具辅助，**人工确认后再删**：

| 工具 | 用途 |
|------|------|
| `pnpm knip` | 失效文件、错误 import、未使用依赖（`knip.json`） |
| `tsc --noEmit` / eslint | 未使用局部量、未使用 import |

- [ ] 失效文件、错误相对路径 import。
- [ ] 死常量 / `@deprecated` 别名 / 无消费方的重复 export。
- [ ] 历史兼容分支、fallback：无消费方则删（允许破坏性重构）。
- [ ] 过度复杂或重复实现：能更简单则建议替换。
- [ ] **禁止**按 knip「Unused exports / Unused exported types」批量删除。

归类用语（写计划时用）：死代码、历史兼容残留、无用代码（import/依赖/资源）、简洁性（去重、必填建模、文件职责）。

## 4. 计划输出模板

- 建议执行项（删 / 并 / 改 / 补），尽量落到文件或 caseId。
- 需用户决策的问题（可附默认建议）。
- 明确不在本次范围的项。
- 工作区若已有未提交相关改动：注明避让策略。
