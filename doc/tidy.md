# 文档、测试与代码 Tidy 流程

文档类型与入口以各文件自身「定位」和 `AGENTS.md` 为准；本文件只定**怎么判该不该动**，不重复定义「每类文档写什么」。

## 1. 流程

按节点推进，先完成一个节点的审核，给用户审批清理方案，执行完后才能进入下一个节点

允许破坏性清理（死代码、兼容残留），但不得改写已发布 SQLite migration 锁清单内的历史 migration。

## 2. 审阅清单

### 2.1 文档 ↔ 实现对齐

核对文档声称的能力、边界、主链路是否与当前代码一致。

- [ ] `AGENTS.md` 指向的路径 / 模块仍存在，且职责描述未明显过时。
- [ ] doc一级下的文档 与实现主链路一致。
- [ ] PRD 目录文档与实际代码是否对齐。
- [ ] ai-harness 目录文档与实际代码是否对齐。
- [ ] test-plan 目录文档与实际代码是否对齐。

### 2.2 文档健康

**清理标准**（建议直接改，仍须进计划获批）：

- [ ] 临时句、过期备注、半截迁移残留、无消费方的重复段落。
- [ ] 错误或错绑编号；同一事实多处拷贝且已漂移 → 收敛到单一真相源，或标出矛盾。
- [ ] 无价值，无意义的语句。

**重构触发**（只写进计划，批准后再做）：

- [ ] 一篇文档混了两种读者目标（例如产品验收 + 工具协议）。
- [ ] 一章膨胀到难以按产品域或主题扫完；或补丁堆到「补丁 > 结构」。
- [ ] 文件边界与 `AGENTS.md` / 目录骨架冲突，需要拆 / 并 / 重写某章。

### 2.3 PRD ↔ 测试计划对齐

核对产品验收与回归设计是否对得上（本步以 PRD 与 `doc/test-plan/**` 为主；case 文件是否可发现作为计划可执行性检查）。

按产品域勾选（`ST-*` 已并入 `doc/prd/workbench.md`，不单开一域）：

- [ ] Settings（`SET-*`）
- [ ] Workbench（`WB-*`，含 `ST-*`）
- [ ] AI 产品相关验收若落在 PRD，同样核对；

检查项：

- [ ] 每个 AC 在对应测试计划中有归属，或标明手动 / 发布前检查 / 由其他域承担。
- [ ] 计划 Oracle 引用的 AC 与 PRD 语义一致（无错绑）。
- [ ] 计划中的 `caseId` 能被 runner 发现；一文件多 case 时计划写明文件归属。
- [ ] 跨域交叉点（未绑目录、帮助入口等）无双边重复硬断言，或写明「只在一侧断言」。

### 2.4 测试分层与清理

- [ ] 分层符合 `doc/test.md`文档设计。
- [ ] 重复或者无意义的测试case。
- [ ] 检查每个测试case是否有价值与无用的设计。

### 2.5 代码整洁

工具辅助，**人工确认后再删**：

| 工具 | 用途 |
|------|------|
| `pnpm knip` | 失效文件、错误 import、未使用依赖（`knip.json`） |
| `tsc --noEmit` / eslint | 未使用局部量、未使用 import |

- [ ] 失效文件、错误相对路径 import。
- [ ] 死常量 / `@deprecated` 别名 / 无消费方的重复 export。
- [ ] 历史兼容分支、fallback：无消费方则删（允许破坏性重构）。
- [ ] 过度复杂或重复实现：能更简单则建议替换。
- [ ] **禁止**按 knip「Unused exports / Unused exported types」批量删除。
