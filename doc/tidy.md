# 文档、测试与代码 Tidy 流程

周期性整理：先审计 → 出计划 → 用户批准 → 再改仓库。未获批前不删除、合并或改写文档、测试与代码。

文档类型与入口以各文件自身「定位」和 `AGENTS.md` 为准；本文件只定**怎么判该不该动**，不重复定义「每类文档写什么」。

## 1. 流程

1. 按第 2 节清单**依优先级**逐项审计（同级内可并行；每项必须有结论，无关则写「不适用」）。
2. 产出「Tidy 计划」：删 / 并 / 改 / 补，以及需拍板的问题。
3. 只执行获批项。
4. 若改了 PRD / 测试计划 / 代码边界，同步 `AGENTS.md` 与对应 `doc/test-plan/**`。

允许破坏性清理（死代码、兼容残留），但不得改写已发布 SQLite migration 锁清单内的历史 migration。

文内互指用「第 N 节」或章节标题，不用 `§`。

## 2. 审阅清单

优先级从上到下：先核对文档是否仍描述真实系统，再做文档清理/重构，再对齐验收与测试计划，最后才是测试去重与代码整洁。否则会在错误文档上做对齐。

每项只出现一次。

### 2.1 文档 ↔ 实现对齐

核对文档声称的能力、边界、主链路是否与当前代码一致（抽查关键路径即可，不要求逐行对照）。

- [ ] `AGENTS.md` 指向的路径 / 模块仍存在，且职责描述未明显过时。
- [ ] 架构 / database / release / ui-style / harness 与实现主链路一致（入口、存储、关键流）。
- [ ] PRD 声称的功能在实现中仍存在；已下线或未做的能力未继续写成现行验收。
- [ ] harness / 工具契约文档与当前 tool schema、投递、graph 行为无硬性矛盾。

发现不一致：优先建议改文档或改代码（二者择一进计划），避免只改测试计划「迁就」错误文档。

### 2.2 文档健康

原则：PRD 保持产品功能与验收；实现与协议细节不进 PRD（已混入的按清理或重构处理）。

**清理标准**（建议直接改，仍须进计划获批）：

- [ ] 临时句、过期备注、半截迁移残留、无消费方的重复段落。
- [ ] 错误或错绑编号；同一事实多处拷贝且已漂移 → 收敛到单一真相源，或标出矛盾。
- [ ] 生成物治理明确：入库 / 按需生成 / 缩成索引。

**重构触发**（只写进计划，批准后再做）：

- [ ] 一篇文档混了两种读者目标（例如产品验收 + 工具协议）。
- [ ] 一章膨胀到难以按产品域或主题扫完；或补丁堆到「补丁 > 结构」。
- [ ] 文件边界与 `AGENTS.md` / 目录骨架冲突，需要拆 / 并 / 重写某章。

### 2.3 PRD ↔ 测试计划对齐

核对产品验收与回归设计是否对得上（本步以 PRD 与 `doc/test-plan/**` 为主；case 文件是否可发现作为计划可执行性检查）。

按产品域勾选（`ST-*` 在 `doc/prd/scheduled-task.md`，并入 Workbench，不单开一域）：

- [ ] Settings（`SET-*`）
- [ ] Workbench（`WB-*`，含 `ST-*`）
- [ ] AI 产品相关验收若落在 PRD，同样核对；纯工具协议归 harness + `ai-test`，不要求塞进产品 PRD

检查项：

- [ ] 每个 AC 在对应测试计划中有归属，或标明手动 / 发布前检查 / 由其他域承担。
- [ ] 计划 Oracle 引用的 AC 与 PRD 语义一致（无错绑）。
- [ ] 计划中的 `caseId` 能被 runner 发现；一文件多 case 时计划写明文件归属。
- [ ] 跨域交叉点（未绑目录、帮助入口等）无双边重复硬断言，或写明「只在一侧断言」。

### 2.4 测试分层与去重

- [ ] 分层符合 `doc/test.md` 与 `ai-test.md` 第 3.4 节：Workbench E2E 不重复工具内部算法；tool / mock / live / unit 职责清晰。
- [ ] 输入、主行为、Oracle 均等价的 case / it：建议删或并。
- [ ] 分层不同、看起来像重复的：保留并写明理由。
- [ ] live 成本重叠：列出供决策，默认不擅自砍。
- [ ] Unit 已被 AI tool 契约完全覆盖的重叠 it：建议删。
- [ ] 覆盖缺口：补测前先确认分类（AI / Settings / Workbench / Unit）。

### 2.5 代码整洁

工具辅助，**人工确认后再删**：

| 工具 | 用途 |
|------|------|
| `pnpm knip` | 失效文件、错误 import、未使用依赖（`knip.json`） |
| `tsc --noEmit` / eslint | 未使用局部量、未使用 import |

- [ ] 失效文件、错误相对路径 import。
- [ ] 死常量 / `@deprecated` 别名 / 无消费方的重复 export。
- [ ] 历史兼容分支、fallback：无消费方则删（允许破坏性重构）。
- [ ] 过度复杂或重复实现：能更简单则建议替换。
- [ ] **禁止**按 knip「Unused exports / Unused exported types」批量删除。

归类用语（写计划时用）：死代码、历史兼容残留、无用代码（import/依赖/资源）、简洁性（去重、必填建模、文件职责）。

## 3. 计划输出模板

- 建议执行项（删 / 并 / 改 / 补），尽量落到文件或 caseId。
- 需用户决策的问题（可附默认建议）。
- 明确不在本次范围的项。
- 工作区若已有未提交相关改动：注明避让策略。
