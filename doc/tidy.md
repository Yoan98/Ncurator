# 文档、测试与代码 Tidy 流程

本文件只定义周期性整理流程，不包含脚本或自动修改逻辑。执行 Tidy 时先审计、汇总并等待用户决策；未获得决策前，不删除、合并或改写项目文档、测试用例和代码。

## 1. 对齐文档与实现

逐份检查项目文档（架构、PRD、测试计划、测试规范、发布文档等）与实际代码、配置、脚本和目录结构：

- 标出实现已经变化但文档未同步的内容。
- 标出文档仍描述、实现已经移除的内容。
- 标出文档之间互相矛盾或范围重复的内容。

## 2. 整理 PRD、测试计划和测试用例

分析 PRD、对应测试计划和全部实际测试用例，提出明确的处理建议：

- 多余的文档或用例：删除建议。
- 目标相同、断言重复的内容：合并建议。
- 实现或需求已有但覆盖缺失的内容：新增建议。
- 定位正确但内容已偏移的文档或用例：调整建议。

## 3. 对齐 Settings / Workbench

对 Settings 和 Workbench 分别完成一条完整链路核对：

`PRD 功能点 → 测试计划 case → 实际测试 case`

核对功能点、验收编号、case ID、测试类型、覆盖范围和关键 Oracle 是否一致。

## 4. 文档检验

- 逐份文档检查定位、内容完整性、与其他文档的边界及重复内容；保持既有文档骨架，只修补内容。
- `architecture` 只保留总架构设计；`test`、`database`、`release`、`tidy`、`ui-style` 分别只维护自身长期规则。
- 文档能约束的规则检查文档与实现是否一致；无法只靠文档约束的规则，继续检查对应代码、配置、目录或测试是否落地。

## 5. 清理代码整洁度

审计代码的整洁度与可维护性，识别死代码、兼容残留、无用代码与可简化实现，汇总成「清理项清单」等待用户决策，不直接删除。

### 5.1 死代码

- 不可达代码：恒真/恒假分支、return/throw 之后的语句、被注释掉的旧实现。
- 未使用导出：export 但全仓无 import 的函数、类型、常量。
- 失效文件：无入口引用、无测试引用的整文件。

### 5.2 历史兼容残留

- 为旧版本/旧格式保留的兼容分支、别名、迁移守卫、fallback 占位。
- 依据 AGENTS 规则 4.1（允许破坏性重构）：确认无消费方后直接删除，不为旧逻辑保留兼容。

### 5.3 无用代码

- 未使用 import（eslint no-unused-vars 覆盖）。
- 未使用局部变量与参数（tsc noUnusedLocals / noUnusedParameters 覆盖）。
- 未使用依赖与脚本：package.json 中无引用的依赖、脚本。
- 未使用资源/资产：未被引用的图片、样式、资源文件。

### 5.4 简洁性 / 简单性优化

- 过度复杂实现替换为更简单方案（AGENTS 4.3）。
- 重复逻辑/重复类型抽象；避免过度抽象（AGENTS 4.2）。
- 无用抽象/接口：仅单一实现的接口、为扩展预留但从未使用的抽象层。
- 可选类型 + 运行时兜底占位 → 建模为必填（AGENTS 4.6）。
- 文件过碎/职责混乱 → 合并或拆分（AGENTS 4.4）。

### 5.5 审计工具

- tsc --noEmit：未使用局部变量与参数。
- eslint：未使用 import 与变量。
- knip：未使用导出、未使用依赖、失效文件（仅审计，不自动删除）。运行 `pnpm knip`，配置见根目录 `knip.json`（入口由 electron-vite 插件自动识别，脚本目录显式列为入口）。

## 6. 清理文档
剔除无效，历史性，无价值的文档，目的是让文档后面好继续维护，清晰，无噪音。

## 6. 汇总与决策

完成审计后汇总现状、差异、清理项和建议，明确需要用户决定的问题；用户确认后再执行。建议可以包含不兼容旧逻辑的重构（如删除死代码、兼容残留），但 Tidy 本身不编写整理脚本。
