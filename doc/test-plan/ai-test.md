# NCurator-Desktop Core AI 测试计划

## 1. 总体目标

本计划用于定义 AI 域正式测试的阶段划分与阶段归属。

## 2. 阶段设计

测试按阶段顺序推进，原则上上一阶段形成稳定结论后，再进入下一阶段。

AI 域正式测试当前分为四个阶段：

1. `tool`
2. `human`
3. `director`
4. `real`

其中：

- `tool / human / director` 属于 `backend`
- `real` 属于 `e2e`

### 2.1 `tool`

做什么：验证 AI 运行依赖的核心工具与工具契约。

为什么：工具层不稳定时，上层执行与编排结论都会失真。

怎么做：以 backend harness 为主，验证单个工具或单类工具是否满足上层调用前提，例如读取、写入、保存、审批、范围约束、失败回传和结果可回看。

### 2.2 `human`

做什么：验证 `human` 作为 AI 执行体，是否能基于明确目标自主推进、处理中断并形成可交付结果。

为什么：工具只是零件，`human` 才决定单任务执行链路能不能真正闭环。

怎么做：以 backend harness 为主，验证单任务执行、工具协作、阻塞收敛、部分交付和 handoff 结构是否稳定。

### 2.3 `director`

做什么：验证 `director` 对整体 AI 链路的编排能力。

为什么：路由、补上下文、任务拆解、阶段切换和最终综合都属于 `director` 的职责；这一层不稳定时，系统会在进入执行前走偏。

怎么做：以 backend harness 为主，统一覆盖 `context / intent / plan / entire` 范围，重点验证路由判断、上下文补齐、任务编排、执行衔接和综合交付。

### 2.4 `real`

做什么：验证真实用户场景下的 AI e2e 完整链路。

为什么：只有在真实模型、真实页面和真实任务输入下完成的 case，才能证明产品路径成立。

怎么做：通过 e2e 验证真实场景测试，覆盖用户输入、页面反馈、运行阻塞、恢复继续、最终交付和可回看结果。

## 3. 阶段归属规则

- AI 正式 case 必须先判断主要验证的是哪一层契约，再归到单一阶段。
- `tool` 只承接工具能力与工具契约验证。
- `human` 只承接单任务执行与单任务交付验证。
- `director` 统一承接路由、补上下文、任务编排和综合交付验证。
- `real` 只承接真实场景 e2e，不承接纯 backend 契约验证。
