# NCurator-Desktop AI Prompt 设计准则

本文只定义 AI prompt 的通用设计原则，不承载 `brain / mouth / intent / plan` 等节点的完整 prompt 草稿。

## 1. 设计目标

- 让 prompt 结构稳定、易读、易维护。
- 让模型先理解任务和上下文，再遵守输出契约。
- 避免 prompt 被实现细节绑死，同时保留足够明确的边界。
- 让不同节点的 prompt 在表达风格上保持一致。

## 2. 推荐结构

- prompt 默认按“角色层、工作方式层、输出规则层、上下文层”组织。
- 主要段落统一使用语义化标签，例如 `<system>`、`<role>`、`<working_style>`、`<principles>`、`<output_rules>`、`<user_context>`。
- 标签用于组织信息，不用于制造过深层级。

推荐基线：

```text
<system>
  <role>...</role>
  <working_style>...</working_style>
  <principles>...</principles>
  <output_rules>...</output_rules>
  <output_example>...</output_example>
</system>

<user_context>
  <task>...</task>
  <context_block>...</context_block>
  <context_block>...</context_block>
</user_context>
```

## 3. 输入组织准则

- 输入部分优先使用自然语言名称，而不是直接暴露字段名。
- 每块输入都应让模型知道“这是什么”和“为什么重要”。
- 默认把输入组织成稳定、可读的文本块，而不是整段原始 JSON。
- 不同类型的信息应拆开提供，例如用户要求、记忆、技能上下文、最近工具结果、最近决策历史摘要、收敛提示。
- 只有在专项设计明确需要时，才保留局部结构化载荷；不要把完整运行态对象原样塞进 prompt。

推荐命名：

- 用户的要求
- 你之前沉淀下来的记忆
- 最近一次工具结果
- 最近决策历史摘要
- 当前的收敛提醒

## 4. 输出规则准则

- 字段名只在 `output_rules`、字段说明和输出示例中集中出现。
- 输出规则要同时说明顶层字段、字段含义、出现条件和允许结构。
- 如果是 JSON 输出，明确写“只输出 JSON，不要输出额外说明”。
- 如果运行时已经支持 schema 约束的结构化输出，优先使用结构化输出能力承接契约。
- 每类关键输出结构至少给一个完整示例；示例应尽量短，但必须完整。

## 5. 约束表达准则

- 约束优先写成稳定原则，而不是冗长的禁止清单。
- 重点限制聚焦在：
  - 不编造事实
  - 不越过职责边界
  - 不输出错误格式
  - 有足够依据时优先收敛
- 只有确实会导致明显错误的地方，才写成强约束。

推荐表达：

- 只基于已经提供的信息组织结果，不要补充新的事实。
- 如果当前依据已经足够，优先结束，而不是重复做同样的动作。
- 字段名只在输出 JSON 中使用。

## 6. 专项 prompt 的边界

- 节点级的行为规范与职责边界，由 `implementation-spec.md` 定义。
- 节点级的输出契约与状态字段，由 `data-definition-and-flow.md` 定义。
- 本文档只负责共性的 prompt 设计方法，不替代专项节点设计。
- 如果后续需要维护完整 prompt 草稿，应优先放在实现附近或专项设计文档中，不放在本文档里。

## 7. 维护规则

- 当通用表达方式发生变化时，先更新本文档，再更新具体 prompt。
- 当节点输出契约调整时，应同步检查对应实现、数据契约文档和实现规范文档。
- 已实现并确认的 prompt 设计，不应继续停留在 `refactor-plan.md` 中。
