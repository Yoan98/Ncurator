# NCurator-Desktop AI Prompt 设计准则

本文只定义 AI prompt 的通用设计方法，不承载节点职责、数据契约、runtime transport 或文件组织细节。

## 1. 文档定位

- 当需要设计 prompt 的整体结构、输入组织方式、输出规则写法或约束表达时，阅读本文。
- 当需要判断某个节点该做什么、不该做什么时，阅读 `implementation-spec.md`。
- 当需要确认结构化输出字段、状态字段或交付契约时，阅读 `data-definition-and-flow.md`。

## 2. 设计目标

- 让 prompt 结构稳定、易读、易维护。
- 让模型先理解任务和上下文，再遵守输出契约。
- 避免 prompt 被运行时细节绑死，同时保留足够明确的边界。
- 让不同节点的 prompt 在表达风格上保持一致。

## 3. 推荐结构

- prompt 默认按“原则层、决策契约层、长期记忆契约层、输出契约层、上下文层”组织。
- 主要段落统一使用语义化标签，例如 `<system>`、`<principles>`、`<decision_contract>`、`<stable_memory_contract>`、`<output_contract>`、`<user_context>`。
- 标签用于组织信息，不用于制造过深层级。
- 单个 prompt 应优先保持单一主线，避免把不同目的的规则混在同一个段落里。

推荐基线：

```text
<system>
  <principles>...</principles>
  <decision_contract>...</decision_contract>
  <stable_memory_contract>...</stable_memory_contract>
  <context_block_guide>...</context_block_guide>
  <output_contract>...</output_contract>
  <output_shape>...</output_shape>
  <examples>...</examples>
</system>

<user_context>
  <task_goal>...</task_goal>
  <context_block>...</context_block>
  <context_block>...</context_block>
</user_context>
```

## 4. 输入组织准则

- 输入部分优先使用自然语言名称，而不是直接暴露内部字段名。
- 输入块默认只说明“这是什么”，不在每个块里重复教模型“应该如何使用它”。
- 默认把输入组织成稳定、可读的文本块，而不是整段原始 JSON。
- 不同类型的信息应拆开提供，例如用户要求、任务笔记、近期过程、主动回看的历史、技能上下文、收敛提示。
- 只有在专项设计明确需要时，才保留局部结构化载荷；不要把完整运行态对象原样塞进 prompt。
- 当 AI 需要自己构造工具参数时，prompt 中应直接暴露该工具的真实输入结构；结构信息应优先从 schema 自动导出，而不是手写维护另一份嵌套字段说明。
- tool prompt 中的 examples 是正式契约的一部分；examples 应展示最小合法输入，复杂/写类工具应补足更完整的合法示例。

推荐命名：

- 用户的要求
- 你的任务笔记
- 最近过程记录
- 更早过程记录
- 主动回看的历史
- 当前的收敛提醒

## 5. 输出规则准则

- 字段名只在 `output_contract`、字段说明和输出示例中集中出现。
- 输出规则要同时说明顶层字段、字段含义、出现条件和允许结构。
- 如果是 JSON 输出，要明确写“只输出 JSON，不要输出额外说明”。
- 如果运行时已经支持 schema 约束的结构化输出，优先使用结构化输出能力承接契约。
- 每类关键输出结构至少给一个完整示例；示例应尽量短，但必须完整。
- 对“当前可直接调用”的工具，prompt 应同时提供：用途、前置条件、schema 自动导出的完整输入结构、返回语义与 examples；不要只暴露浅层必填参数名。
- 当节点本身输出结构化 JSON 时，prompt 中的输出 shape 也应优先从真实输出 schema 自动导出；语义规则与 shape 分离，前者手写、后者自动生成。
- prompt 中的原则、决策契约、长期记忆契约与输出契约应分层表达：前者负责工作方式和职责边界，后者只负责输出层规则。

## 6. 约束表达准则

- 约束优先写成稳定原则，而不是冗长的禁止清单。
- 重点限制聚焦在：
  - 不编造事实
  - 不越过职责边界
  - 不输出错误格式
  - 有足够依据时优先收敛
- 只有确实会导致明显错误的地方，才写成强约束。
- prompt 应优先暴露能力边界、结果语义和客观运行事实，不应把推荐动作路径写成固定操作手册，以保留模型自主判断空间。

推荐表达：

- 只基于已经提供的信息组织结果，不要补充新的事实。
- 如果当前依据已经足够，优先结束，而不是重复做同样的动作。
- 字段名只在输出 JSON 中使用。

## 7. 风格一致性准则

- 不同节点的 prompt 应保持同一套表达习惯，不要每个节点都换一套语言风格。
- 同一类概念应使用同一组名称，例如任务、记忆、技能、历史、收敛提示。
- 输出示例应短而完整，帮助模型快速理解目标格式，而不是堆很多变体。
- 不要把 transport、事件分发、工具实现细节混进 prompt 设计文档中。

## 8. 专项 prompt 的边界

- 节点级行为规范与职责边界，由 `implementation-spec.md` 定义。
- 节点级输出契约与状态字段，由 `data-definition-and-flow.md` 定义。
- 本文档只负责共性的 prompt 设计方法，不替代专项节点设计。
- 如果后续需要维护完整 prompt 草稿，应优先放在实现附近或专项设计文档中，不放在本文档里。

## 9. 维护规则

- 当通用表达方式发生变化时，先更新本文档，再更新具体 prompt。
- 当节点输出契约调整时，应同步检查对应实现、数据契约文档和实现规范文档。
- 已实现并确认的 prompt 设计，不应继续停留在 `refactor-plan.md` 中。
