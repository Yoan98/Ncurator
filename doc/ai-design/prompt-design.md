# NCurator-Desktop AI Prompt 设计准则

## 1. 适用范围

- 当需要新增、重写或评审 AI prompt 时，阅读本文档。
- 当需要统一 prompt 的角色表达、上下文组织、标签结构、输出规则或示例写法时，阅读本文档。
- 本文档只定义通用设计准则，不承载某个具体节点的完整 prompt 草稿。

## 2. 设计目标

- 让 prompt 结构稳定、易读、易维护。
- 让模型先理解任务和上下文，再遵守输出契约。
- 避免 prompt 被实现细节绑死，同时又保留足够明确的输出边界。
- 让不同节点的 prompt 虽然职责不同，但仍共享一套统一表达风格。

## 3. 分层原则

设计 prompt 时，默认按下面四层组织：

1. 角色层
   - 先说明模型此刻扮演什么角色。
   - 角色描述使用自然语言，不直接把实现名词作为 prompt 主体。
2. 工作方式层
   - 描述应该如何理解任务、如何做判断、如何组织输出。
   - 这里写思考方式、表达风格和优先级，而不是 schema 细节。
3. 输出规则层
   - 只在这一层明确字段名、字段含义、输出格式和必要示例。
   - 结构必须清晰、稳定、可直接映射到程序契约。
4. 上下文层
   - 用易理解名称描述输入信息。
   - 让模型知道“这是什么信息、为什么重要”，而不是只看到字段名。

## 4. 标签结构准则

- prompt 的主要段落统一使用 XML 风格标签包裹，例如：
  - `<system>`
  - `<role>`
  - `<working_style>`
  - `<output_rules>`
  - `<user_context>`
- 标签命名要语义化，避免随意缩写。
- 同一类 prompt 尽量保持标签结构稳定，便于后续拼接、调试、替换和对比。
- 标签用于组织信息，不用于制造复杂层级；层数应尽量克制。

推荐结构：

```text
<system>
  <role>...</role>
  <working_style>...</working_style>
  <principles>...</principles>
  <output_rules>...</output_rules>
  <output_example>...</output_example>
</system>

<user_context>
  <task>...</task>
  <context_block>...</context_block>
  <context_block>...</context_block>
</user_context>
```

## 5. 角色表达准则

- 角色要用模型容易理解的自然语言来描述。
- 优先写“你现在扮演一个怎样的人 / 负责怎样的事情”。
- 不要一上来写内部实现术语，例如 graph、node、schema、stage、contract。
- 可以保留少量必要的产品名词，但不要让它主导 prompt。

推荐：

- “你现在扮演一个负责分析情况并决定下一步的人”
- “你现在扮演一个负责把最终结果清楚表达给用户的人”

不推荐：

- “你是 human.brainNode”
- “你是 graph 中的 finalize stage”

## 6. 输入组织准则

- 输入部分优先使用自然语言名称，而不是直接暴露字段名。
- 每块输入都应让模型知道“这是什么”和“它为什么重要”。
- 不同类型的信息要拆开，不要把所有内容混成一大段 JSON。

推荐命名：

- 用户的要求
- 你之前沉淀下来的记忆
- 最近一次工具结果
- 上一轮已经做出的决定
- 上一轮决定进入的下一步动作
- 当前的收敛提醒

不推荐直接在输入部分堆：

- `brainMemory.inside`
- `lastBrainDecision.decision`
- `state.turn.incoming`

字段名可以在输出规则部分单独解释，但不宜主导输入叙述。

如果需要让模型回看上一轮决策，优先提供一个精简视图，只保留：

- 上一轮的判断内容
- 上一轮决定进入的下一步动作
- 该动作携带的关键信息

不要把整个原始状态对象或无关字段原样回灌给模型。

## 7. 输出规则准则

- 字段名只在输出规则、字段说明和输出示例中集中出现。
- 输出规则要同时说明：
  - 顶层字段有哪些
  - 每个字段表示什么
  - 哪些字段在什么情况下出现
  - 允许的值或结构
- 尽量提供至少一个完整输出示例。
- 如果是 JSON 输出，明确写“只输出 JSON，不要输出额外说明”。

推荐写法：

```text
<output_rules>
  你必须只输出 JSON，不要输出任何额外说明。

  顶层字段固定为：
  - summary：表示本轮结果摘要
  - nextAction：表示下一步动作
</output_rules>
```

## 8. 约束表达准则

- 约束优先写成稳定原则，而不是无止境细分的禁止项。
- 重点限制应聚焦在：
  - 不编造事实
  - 不越过职责边界
  - 不输出错误格式
  - 有足够依据时优先收敛
- 只有确实会导致明显错误的地方，才写成强约束。
- 不要为了追求“绝对安全”而把 prompt 写成无法工作的规则清单。

推荐表达：

- “只基于已经提供的信息组织结果，不要补充新的事实。”
- “如果当前依据已经足够，优先结束，而不是重复做同样的动作。”
- “字段名只在输出 JSON 中使用。”

不推荐表达：

- 把所有边界情况逐条枚举到几十条
- 把实现细节和字段限制散落到每个段落里重复出现

## 9. 示例准则

- 每类关键输出结构至少给一个完整示例。
- 示例应尽量短，但必须完整。
- 示例文字要真实、自然，不要用占位式空话。
- 如果输出存在多个分支，优先为每个分支各给一个示例。

## 10. 不同类型 Prompt 的差异

虽然可以共用一套设计准则，但不同职责的 prompt 仍需要分别设计：

- 决策型 prompt
  - 核心是判断下一步做什么。
  - 如果需要回看上一轮决策，应优先提供“上一轮判断 + 上一轮动作”的精简视图。
- 交付型 prompt
  - 核心是把已有结论稳定表达出来。
- 路由型 prompt
  - 核心是判断进入哪条链路。
- 规划型 prompt
  - 核心是把复杂目标拆成可执行任务。

本文档只定义它们共用的设计方法，不替代每种 prompt 的专项设计。

## 11. 维护规则

- 某个具体 prompt 的草稿和专项设计，放在对应领域文档中维护。
- 当通用表达方式发生变化时，先更新本文档，再更新具体 prompt 文档。
- 当输出字段调整时，应同步检查：
  - 对应实现代码
  - 对应数据契约文档
  - 对应专项设计文档
