## Context

当前系统将本地文件与网页统一落到 `document/chunk` 检索模型中，但本地文件入口仍是“上传并复制到应用私有目录后导入”，聊天输入区的 `@` 也只支持已导入文档 ID。该实现适合一次性导入，不适合“长期挂载多个本地资料目录、按目录树理解范围、在聊天中统一选择本地与网页资料”的新产品模型。

这次改造同时涉及存储模型、IPC 契约、聊天交互、资料管理页和 AI 运行时范围语义，属于跨 Main / Shared / Renderer 的结构性变更。项目又明确允许重构且不兼容旧本地文件导入逻辑，因此设计目标不是在旧模型上打补丁，而是将“资料来源”和“检索索引”拆成两个层次：

- 资料来源层：描述用户配置了哪些工作空间、网页资料，以及这些来源下有哪些目录/文件节点。
- 准备与检索层：描述哪些资料已被“准备”为可检索文档，哪些仍只能作为原始来源供 AI 决定是否直接读取。

约束条件：

- 必须遵守现有 AI 架构边界，Main Graph 不直接执行能力，Human Subgraph 通过 tool 决策推进。
- 存储层继续以 LanceDB 分层封装为唯一入口，不在业务逻辑中直接操作底层连接。
- 工作空间必须受 workspace boundary 约束，未准备文件的直接读取不能突破现有安全边界。
- 不允许嵌套工作空间；文件移动/重命名按“删除 + 新增”处理。
- 工作空间 UI 仅展示目录和当前支持的文件类型（首期 `pdf`、`docx`）；网页资料保留独立来源，不并入目录树。

## Goals / Non-Goals

**Goals:**

- 建立以“资料来源”为中心的产品模型，支持多个非嵌套工作空间与独立网页资料来源。
- 为每个工作空间持久化目录树快照、文件状态、最近扫描/准备结果，并支持一键准备与差异同步。
- 继续复用现有 `document/chunk` 检索能力作为“已准备资料”的统一索引层，避免重写检索主链路。
- 让聊天 `@` 能统一选择工作空间、目录、文件和网页资料，并向 AI 传入结构化范围信息。
- 让 AI 在范围内自行决定优先使用本地检索还是直接读取未准备文件，但搜索模式只使用已准备范围。
- 明确移除旧的本地文件上传导入与自动复制逻辑，减少双轨模型和兼容代码。

**Non-Goals:**

- 不实现文件重命名/移动检测；目录内路径变化统一按删除 + 新增处理。
- 不实现工作空间的实时文件系统监听；首期仅支持显式扫描/准备。
- 不将网页资料并入工作空间目录树，也不支持网页自动定时刷新。
- 不在本次设计中扩展新的文件解析类型，仍以 `pdf/docx` 为首期范围。
- 不保证旧本地文件导入记录继续可见或可迁移；旧逻辑可直接下线。

## Decisions

### 1. 将“资料来源”与“检索文档”拆成两层模型

决策：

- 保留现有 `document/chunk` 作为检索索引层。
- 新增工作空间来源与节点快照表，用于记录工作空间、目录节点、文件节点及其准备状态。
- 网页资料继续使用 `document/chunk` 作为已准备文档来源，但在来源管理视图中额外补充“网页来源”展示模型。

建议的数据实体：

- `workspace_source`
  - `id / name / root_path / status / last_scan_at / last_prepare_at / last_error / created_at / updated_at`
- `workspace_node`
  - `id / workspace_id / parent_id / kind(directory|file) / name / relative_path / absolute_path / file_ext / exists / size / mtime_ms / content_hash / prepare_status / document_id / last_prepared_at / last_error / created_at / updated_at`
- `document`
  - 继续作为已准备文档真相来源，但本地文件文档必须由 `workspace_node.document_id` 反向绑定；网页资料仍直接使用 document 记录

其中 `prepare_status` 建议统一枚举为：

- `not_prepared`
- `preparing`
- `prepared`
- `stale`
- `failed`
- `missing`

原因：

- 用户理解的是“资料来源”和“是否准备好”，不是 LanceDB 中的一条 document 记录。
- 继续把目录树状态塞进 `document` 会导致目录节点、未准备节点、缺失节点都无处表达。
- 检索层继续使用 `document/chunk`，可以最大化复用现有搜索、RRF 融合和文档约束能力。

备选方案：

- 直接扩展 `document` 表承载工作空间、目录树和状态。
  - 放弃原因：目录节点不是 document；未准备文件也还不是可检索 document；模型会迅速失真。

### 2. 工作空间采用“扫描快照 + 显式准备”模型，而不是自动监听

决策：

- 工作空间配置后立即做一次目录扫描，生成目录树快照。
- “一键准备”先执行差异扫描，再按用户选择的模式决定处理新增、删除、变更。
- 差异判定使用 `workspaceId + relativePath` 作为主键语义，重命名/移动视为删除 + 新增。
- 变更检测采用两段式：
  - 快速比较：`size + mtimeMs`
  - 命中疑似变更时再计算 `contentHash`

建议准备模式：

- `full`: 新增 + 删除 + 变更
- `presence_only`: 仅新增 + 删除
- `changes_only`: 仅变更

原因：

- 用户明确希望不同耗时路径可选，准备模式必须直接对应耗时差异。
- 不做实时监听能显著降低首期复杂度，也避免跨平台文件事件一致性问题。
- 使用 `relativePath` 作为身份能自然满足“不允许嵌套工作空间”和“移动视为新增删除”的规则。

备选方案：

- 用文件系统监听持续维护快照。
  - 放弃原因：复杂度高，错误恢复难，且并非当前需求必需。

### 3. 本地文件准备不再复制源文件，直接读取原路径；旧本地导入链路整体删除

决策：

- 废弃 `DOCUMENTS_PATH` 本地文件复制模型。
- 本地文件准备时直接读取工作空间内的原始绝对路径，通过现有解析/切分/嵌入流程生成或刷新 `document/chunk`。
- 刷新同一路径文件时尽量复用原有 `document_id`，只替换文档元数据与 chunks，避免准备状态和范围引用漂移。
- 旧本地文件上传 IPC 与 UI 入口直接移除，不做双轨保留。

原因：

- 用户对“资料来源”的心智是本地目录，不是导入后的副本。
- 复制模型会带来路径漂移、双份存储、删除后状态不一致等问题。
- 既然不要求兼容旧逻辑，继续保留复制链路只会增加迁移成本和歧义。

备选方案：

- 保留复制逻辑，仅把导入入口改名为工作空间准备。
  - 放弃原因：违背用户对工作空间的理解，也让“本地修改后为什么系统没变”更难解释。

### 4. 聊天 `@` 传递“统一范围节点”，而不是只传 document ids

决策：

- AI 运行时输入从仅有 `selectedDocumentIds` 扩展为：
  - `selectedDocumentIds`: 已准备且可直接检索的文档
  - `selectedSourceScopes`: 用户在 `@` 中选中的工作空间/目录/文件/网页资料节点
- 聊天模式下，`selectedSourceScopes` 表示“优先参考范围”，用于提示 AI 优先在这些资料中检索、读取或分析，而不是绝对过滤条件。
- 搜索模式下，范围语义保持严格过滤，仅允许已准备范围参与搜索。
- 每个范围节点至少包含：
  - `scopeType`
  - `sourceId`
  - `nodeId?`
  - `label`
  - `absolutePath?`
  - `relativePath?`
  - `documentIds`
  - `hasUnpreparedFiles`
  - `sourceType`
- 用户显式选择的范围项必须原样保留；即便父子节点重叠，也只对底层 `documentIds` 去重，不隐式改写用户选择表达。

聊天 `@` 的运行时语义：

- `@` 只负责圈定范围，不强制指定工具。
- 若范围内有已准备文档，AI 可优先使用本地知识库检索。
- 若范围内存在未准备本地文件，AI 可结合任务目标自行决定是否走工作空间内的文件读取/终端能力。
- 若已选范围不足以完成任务，AI 应保留该范围作为优先参考，而不是自动越权扩大到未选中的本地资料；可以提示用户补充范围、补充资料或先准备文件。
- 搜索模式不传未准备文件范围，只允许已准备范围进入检索。

原因：

- 单纯的 `documentId[]` 无法表达目录、工作空间、未准备文件或网页来源分组。
- 用户明确希望“由 AI 决定怎么走”，因此前端不应把 `@` 硬编码成检索工具选择器。
- 用户对 `@` 的核心预期是“优先参考这些资料”，而不是“强制只能看这些资料”；将聊天和搜索使用同一套严格过滤语义会放大误解。
- 结构化 scope 能同时服务聊天、搜索和后续更多文件类型扩展。

备选方案：

- 继续只传 `documentId[]`，目录和工作空间在前端预展开。
  - 放弃原因：未准备文件无法表达；网页与目录混选会丢失来源语义；AI 无法知道自己被圈定的是目录还是具体文件。

### 5. 未准备本地文件不进入搜索索引，但允许 AI 在工作空间边界内直接读取

决策：

- 搜索模式严格只允许已准备范围。
- 聊天模式下，未准备本地文件不会自动临时建索引；而是作为范围提示交给 AI，由现有 workspace-bound 能力决定是否直接读取。
- 设计上优先复用已有 `terminal_exec` / `docx` 等 workspace-bound 能力，不新增“无边界临时读取”旁路。
- 对 `pdf` 等当前不适合直接稳定读取的类型，本次变更不强制承诺“未准备即可正式读取”；实现上应优先通过正式解析器暴露安全读取能力，而不是依赖系统命令的偶然表现。若当前没有合适 capability，AI 可提示用户先准备。

原因：

- 用户要求未准备文件“可以使用”，但不希望规则写死。
- 搜索模式需要确定性和稳定结果，因此只能依赖已准备索引。
- 直接绕过 workspace 安全边界会破坏现有 AI 架构约束。

备选方案：

- 用户选中未准备文件时强制先准备。
  - 放弃原因：与“AI 自己决定怎么走”的产品要求冲突。
- 为未准备文件自动临时建索引。
  - 放弃原因：耗时重、状态隐蔽，也会让“准备”和“临时读取”边界变模糊。

### 6. 资料管理页按“工作空间”和“网页资料”分区展示，但在 `@` 里统一选择

决策：

- 左侧/主内容页采用“资料来源”心智，至少分成两个板块：
  - `工作空间`
  - `网页资料`
- 工作空间展示卡片摘要、目录树、状态计数、准备入口和进度。
- 网页资料保持列表/分组视图，支持新增和重新抓取。
- 聊天 `@` 选择器统一展示四类节点：
  - 工作空间
  - 目录
  - 文件
  - 网页资料

原因：

- 工作空间和网页资料的更新机制不同，管理页混为一谈会让用户难以理解“为什么本地目录会更新，网页不会”。
- 在聊天 `@` 里统一入口，用户只需理解“我在圈定资料范围”。

备选方案：

- 管理页也完全合并成一棵树。
  - 放弃原因：网页资料没有天然目录结构，硬合并只会制造伪层级。

### 7. 迁移策略只保留网页资料，旧本地文件记录直接淘汰

决策：

- 升级后保留现有网页类型 document/chunk 数据。
- 旧本地文件导入记录不再出现在新工作空间模型中，也不尝试自动映射回工作空间。
- 旧复制文件目录可在迁移完成后由清理逻辑移除，或在首次进入新版资料来源页时提示用户旧本地导入已失效。
- 历史聊天消息保留原始文本，但若其引用的是已淘汰的旧本地导入来源，UI 应将其标记为历史失效来源，并提示用户重新配置工作空间，而不是继续尝试打开失效路径。

原因：

- 旧本地导入记录缺少可靠的工作空间归属、目录层级与原始来源语义。
- 用户已明确允许不兼容旧逻辑，继续迁移这些历史副本收益低、复杂度高。

备选方案：

- 尝试基于 `file_path/name` 自动反推原工作空间。
  - 放弃原因：现有数据指向的是复制后的私有路径，不是用户原始目录，无法可靠恢复。

## Risks / Trade-offs

- [Risk] 工作空间扫描和内容哈希在大目录上耗时明显 → Mitigation: 将扫描、差异判定和准备拆成独立阶段，UI 展示进度，并提供轻量模式（仅增删 / 仅变更）。
- [Risk] 未准备文件允许 AI 自行读取，行为可能不稳定 → Mitigation: 在 prompt 和工具描述中明确“已准备优先检索，未准备可按需读取”，同时把搜索模式限制为已准备范围。
- [Risk] `pdf` 未准备读取质量不稳定 → Mitigation: 后续实现优先补“正式解析读取”能力，避免依赖 shell 输出质量。
- [Risk] 本次移除旧本地导入逻辑后，历史数据会出现断层 → Mitigation: 明确作为破坏性变更处理，仅保留网页资料，首屏或迁移提示清楚说明旧本地导入需重新配置工作空间。
- [Risk] 目录树快照、准备状态和 `document/chunk` 之间的绑定关系可能失配 → Mitigation: 以 `workspace_node.document_id` 作为唯一绑定点，所有本地文件刷新先删旧 chunks 再写入同一 document id。
- [Risk] 工作空间边界和聊天 `@` 范围同时存在，用户可能混淆二者作用 → Mitigation: UI 文案明确区分“工作空间是文件访问边界”，“@ 是本次提问的资料范围”。
- [Risk] 不同路径表示或符号链接可能绕过重复/嵌套校验 → Mitigation: 基于规范化后的真实路径执行判重与边界校验。
- [Risk] 并发准备或部分失败会让状态难以理解 → Mitigation: 同一工作空间只允许一个活跃准备任务，并把部分失败下沉到文件节点状态与错误提示。

## Migration Plan

1. 在 LanceDB storage 层新增工作空间与节点快照表，并在 shared 类型中加入统一范围选择模型。
2. 下线旧本地文件上传导入 IPC、preload API 和页面入口，保留网页资料导入链路。
3. 将知识库管理页重构为“资料来源”页，分为工作空间和网页资料两个板块。
4. 实现工作空间扫描、差异判定、准备执行和状态更新链路，复用现有文件解析与 `document/chunk` 存储。
5. 重构聊天输入区与搜索范围模型，改为统一范围选择，并将结构化 scope 传入 AI runtime。
6. 更新 AI prompt / tool 输入契约，使 AI 能理解“已准备优先检索、未准备可按需直接读取”的范围语义。
7. 首次升级时仅保留网页资料；旧本地文件导入记录不迁移。若保留历史 LanceDB 数据，需清理或隐藏旧 file 类型文档，避免与新模型混用。

回滚策略：

- 由于这是明确的破坏性重构，产品层面不提供运行时回滚兼容。
- 开发阶段若需回滚，仅回退代码与新表结构变更，不要求保留已废弃的旧本地文件导入数据。

## Open Questions

- 网页资料在 `@` 选择器中是否需要首期就支持站点分组/来源分组，还是先以单网页项为主。
- 工作空间 UI 是否允许“只扫描不准备”，作为独立显式动作暴露给用户；当前设计默认配置后立即扫描、准备前再次扫描。
