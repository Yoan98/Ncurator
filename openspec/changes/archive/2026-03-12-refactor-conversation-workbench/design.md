## Context

当前 Renderer 将搜索页与聊天页拆成两套入口与页面状态：搜索直接调用本地知识库检索，聊天页消费 AI 运行事件流并维护独立的右侧面板、计划区、审批区和输入区。该结构在“问答”与“检索”阶段尚可工作，但一旦引入“AI 读取文档 -> 生成草稿 -> 用户逐块确认 -> 最终提交”的连续流程，现有页面分裂、事件直连页面组件和直接写盘语义都会成为扩展阻力。

同时，现有 AI 架构已经明确了 main/human 双层边界、`human_step.publicNarrative` 的 UI 语义、`human_diagnostic` 的内部调试语义，以及 file artifact / approval / workspace 等运行时事件契约。这意味着本次重构不需要重做 AI 编排，而是需要在 Renderer、Shared 契约、草稿存储和 docx 提交语义上建立新的统一工作台模型。

## Goals / Non-Goals

**Goals:**
- 将首页统一为单一会话工作台，在同一会话中承载 `AI 对话` 与 `纯搜索` 两种运行模式。
- 将 AI 运行过程渲染为可回放的步骤时间线和检查器，而不是“最新事件覆盖式”的右侧输出。
- 为文档编辑建立“草稿生成 -> 审阅确认 -> 最终提交”的安全流程，默认不在运行阶段改写真实文档。
- 为 docx 首次落地提供稳定的草稿审阅模型，并为 pdf、xlsx、pptx、md、txt 的后续接入预留统一抽象。
- 保持 Main/Renderer/Shared 边界清晰，避免把新的跨进程契约继续堆回单页状态里。

**Non-Goals:**
- 重写现有 main/human 图编排或改变 AI 架构的主流程边界。
- 在本次设计中实现完整的多格式编辑能力；V1 仅要求设计抽象兼容，实际实现优先 docx。
- 在 Renderer 中暴露原始内部推理、prompt 或 `human_diagnostic` 内容。
- 构建富文本 WYSIWYG 编辑器；本次只覆盖审阅、预览、差异和提交，不覆盖自由编辑器体验。

## Decisions

### 1) 统一首页采用“单页工作台 + 双运行模型”，而不是把纯搜索强行并入 AI runner

首页将只保留一个会话工作台页面，并在输入区提供 `AI 对话` 与 `纯搜索` 两种模式。`AI 对话` 继续走现有 AI runtime；`纯搜索` 直接使用本地知识库搜索链路，不进入 main/human 图，也不依赖 LLM。两种模式都会被投影成统一的会话回合与时间线视图模型。

Rationale:
- 纯搜索本质是本地检索，不需要 plan、tool loop 或 finalization token 流，强行并入 AI runner 会增加延迟和复杂度。
- 单页统一能消除“先搜索再跳聊天”的产品割裂，同时保留搜索模式的低成本与确定性。
- 同一会话支持混合回合，用户可以在检索后直接继续 AI 编辑或提问。

Alternatives considered:
- 保留 `SearchPage` 与 `ChatPage`，只在视觉上做统一：拒绝，因为交互模型和状态仍然割裂。
- 让纯搜索也走 AI runner：拒绝，因为检索场景不需要模型编排，且会让搜索结果展示绑定 AI 事件流。

### 2) 中央区显示“最终回答 + 执行日志卡”，右侧显示“时间线 + 检查器”

每个 AI 回合在中央区只保留一条最终 assistant 回答，并配套一个可折叠的 `AssistantRunCard` 展示计划、步骤流、阻塞状态与完成状态。右侧面板不再维护“最新结果”单槽，而是拆成上部时间线列表和下部检查器详情。搜索回合会复用同一布局，但只展示简化的检索步骤与结果。

`AssistantRunCard` 只使用 `human_step.publicNarrative`、plan/task 事件、审批/阻塞事件和结果摘要，不展示 `human_diagnostic` 或原始推理文本。右侧检查器则消费步骤详情、检索结果、文档片段、diff、预览和审批信息。

Rationale:
- 逐步把每个步骤都渲染成聊天气泡会迅速污染会话流，用户很难找到最终回答。
- “中央叙事，右侧证据”的布局更符合用户的心智模型：左边看 AI 正在做什么，右边看它实际读了什么、改了什么。
- 该设计能自然兼容 plan、approval、workspace_required、non_local_permission 等阻塞型步骤。

Alternatives considered:
- 为每个 `human_step` 单独创建 assistant message：拒绝，因为消息数量会失控，且不利于最终回答聚合。
- 保留当前右侧单面板并继续按事件覆盖：拒绝，因为无法回溯，也无法承载草稿审阅。

### 3) 引入 Renderer 投影层，页面不再直接消费原始 `AiRunEvent` 联合类型

Renderer 将新增统一视图模型层，把 AI 事件流和搜索结果流投影为统一的 `ConversationRun`、`TimelineEntry`、`InspectorPayload`、`ReviewEntry` 等视图模型。页面只依赖投影结果，不再在单页内部直接用 `if (evt.type === ...)` 处理所有运行细节。

建议的数据边界：
- Shared：新增运行审阅与提交流程的跨进程契约类型。
- Renderer types：定义会话工作台视图模型与组件输入模型。
- Main：保留运行态细节与草稿聚合逻辑，不向 Renderer 暴露内部临时结构。

Rationale:
- 当前聊天页把事件监听、状态聚合和 UI 布局耦合在一个组件中，已经不适合继续承接搜索模式、审阅中心和多格式 diff。
- 搜索模式并不天然拥有 `AiRunEvent`，统一投影层可以让“真实 AI run”和“搜索伪时间线”共享 UI 组件。
- 未来增加新事件或格式时，主要变动可限制在投影层与渲染器注册表，而不是再次膨胀页面组件。

Alternatives considered:
- 保持页面直接消费原始事件联合类型：拒绝，因为会把新的审阅、提交流程继续堆到巨型页面里。
- 在 Main 端直接生成完整 UI ViewModel：拒绝，因为会把 Renderer 展示策略反向侵入 Main 运行时。

### 4) 文档编辑统一改为“草稿审阅 / 最终提交”两阶段模型

所有可编辑文档在 AI 运行阶段只允许生成草稿与预览，不允许直接写回用户真实文件。运行完成后，系统进入 `review_pending` 状态，展示按文档聚合的草稿列表和按变更单元拆分的可确认项；用户对每个变更单元执行接受/拒绝后，系统基于“已接受变更”重建最终草稿，再执行一次显式提交写盘。

设计上的核心聚合对象：
- `DraftReview`：一次 AI 回合产生的待审阅结果集合。
- `DraftDocument`：某个源文档对应的草稿文档。
- `DraftChangeUnit`：最小确认单元，按格式可映射为 block、cell、slide、hunk 等。
- `DraftCommitJob`：最终提交动作及其结果。

每个 `DraftDocument` 都必须保存源文件身份信息，例如源路径、版本戳、mtime 或内容摘要。提交前必须再次校验源文件未被外部修改；若源文件已变化，系统阻止提交并要求用户重新生成或手动处理冲突。

Rationale:
- 这满足“用户最终确认前不改真实文档”的核心产品要求。
- 现有 docx 快照历史与 rollback 能力可直接作为草稿模型底座，但必须把真实写盘从运行阶段挪到提交阶段。
- 引入持久化草稿后，用户切会话、重启应用或延后确认时不会丢失上下文。

Alternatives considered:
- 保留运行中直接 `save` 的默认行为，只在 UI 上补一层提示：拒绝，因为这无法满足真正的 staged review 语义。
- 只在内存中保存草稿：拒绝，因为运行结束或应用退出后审阅状态会丢失。

### 5) 以“格式适配器 + 渲染器注册表”支撑多格式差异与提交，而不是用单一文本 diff 泛化所有文档

系统将引入多格式草稿适配器，至少区分以下责任：
- `DraftAdapter`：从某种格式的编辑结果中生成 `DraftChangeUnit`。
- `DiffRenderer`：在审阅中心渲染该格式的差异视图。
- `CommitAdapter`：将已接受的变更安全提交到真实文件。

V1 以 docx 为首个完整适配器。md/txt 可以退化为文本 hunk；xlsx 使用 cell/range；pptx 使用 slide/shape；pdf 不承诺结构化原位编辑，优先按“预览差异 + 导出新文件或批注结果”建模。

Rationale:
- 文档格式之间的最小确认单元和预览方式差异巨大，用一个统一文本 diff 会在 xlsx、pptx、pdf 上失真。
- 统一抽象层能让审阅中心保持相同交互骨架，同时允许格式特化。
- 先把 pdf 明确为特殊格式，能避免对外承诺不稳定的“精确原位编辑”。

Alternatives considered:
- 所有格式统一退化为文本 before/after：拒绝，因为无法表达表格、幻灯片或页面区域差异。
- 为每种格式单独建设完全不同的审阅页面：拒绝，因为会让用户体验和实现边界碎片化。

### 6) 事件与 IPC 需要扩展为“运行事件 + 审阅契约”双轨模型

AI 运行时继续使用现有 `AiRunEvent` 主事件流承载 plan、human_step、tool_call、approval、artifact 等运行过程；审阅与提交则通过新的 Shared 契约和 IPC 能力暴露，例如：草稿列表、草稿详情、变更单元决策、最终提交、提交结果。对于需要在运行时即时进入 UI 的关键节点，可增加与草稿相关的稳定事件或事件引用字段，但不把完整审阅状态全部塞进单一事件流里。

搜索模式不会强制复用 `AiRunEvent`，而是在 Renderer 投影层生成与 AI 运行相同形状的时间线项。这样可以保持搜索体验轻量，同时复用统一的工作台组件。

Rationale:
- 运行过程是流式、短生命周期的；审阅与提交则可能跨会话、跨应用生命周期存在，二者不适合完全用同一种瞬时事件模型承载。
- 使用独立 IPC 可以让审阅中心在会话恢复时重新加载状态，而不依赖“保留完整历史事件流”。
- 事件流只保留 UI 实时反馈所必需的信息，可以减少 Shared 联合类型继续膨胀。

Alternatives considered:
- 把完整草稿审阅状态都编码进 `AiRunEvent`：拒绝，因为生命周期过长、恢复复杂，且会使事件语义失焦。
- 完全不发草稿相关事件，只靠提交后刷新：拒绝，因为用户会失去运行完成到进入审阅之间的反馈连续性。

## Risks / Trade-offs

- [Risk] 单页工作台会让首屏状态和组件数量明显增加。  
  Mitigation: 使用明确的投影层和组件边界，把运行状态、会话状态、审阅状态拆开，而不是继续堆在单页组件里。

- [Risk] 搜索模式与 AI 模式共用同一会话后，用户可能混淆 `@` 的“优先参考”与“严格过滤”语义。  
  Mitigation: 在输入区对模式与范围语义做显式提示，并在搜索模式下把范围展示为硬过滤标签。

- [Risk] 草稿持久化会引入新的存储模型与清理策略。  
  Mitigation: 在 StorageService 下增加独立 domain store，显式记录生命周期状态，并在提交/取消/过期时统一清理草稿与预览产物。

- [Risk] docx 从直接保存改为 staged commit 后，现有运行链路和测试会出现行为断裂。  
  Mitigation: 先在 Shared 契约和 Main 运行态上引入新语义，再同步调整 Renderer 与测试，避免混用新旧完成模型。

- [Risk] 未来 pdf/xlsx/pptx 的最小确认单元可能比 docx 复杂得多。  
  Mitigation: V1 只要求建立适配器接口和审阅中心骨架，复杂格式逐个接入，不在本次设计里承诺全部实现。

- [Risk] 用户在审阅阶段外部修改了源文件，可能导致提交冲突。  
  Mitigation: 在 `DraftDocument` 中记录源版本信息，提交前强制校验并阻止基于过期源文件的提交。

## Migration Plan

1. 在 Shared 中定义统一会话工作台、草稿审阅和提交流程的契约类型，并补充必要的运行事件扩展字段。
2. 在 Main 中新增草稿审阅服务与存储域，调整 docx 能力默认完成语义，使运行阶段只生成草稿与预览，不直接写回真实文件。
3. 在 Renderer 中建立运行投影层、统一工作台页面和右侧时间线/检查器骨架，同时保留现有搜索/聊天能力的功能对齐。
4. 接入审阅中心与 docx 适配器，完成逐块接受/拒绝、最终提交、冲突校验与结果反馈链路。
5. 将首页路由切换到统一工作台，移除独立搜索页切换逻辑，并同步改造 NotificationCenter 与自动化定位契约。
6. 补齐 renderer contract、e2e 和 main runtime 测试，覆盖搜索模式、AI 执行时间线、草稿恢复、部分确认和最终提交。

Rollback strategy:
- 在统一工作台未达到基本对齐前，保留旧页面组件与旧路由映射作为短期回退手段。
- 若草稿提交流程导致主链路不稳定，可临时关闭审阅入口并退回只读预览模式，同时保留运行事件时间线改造。
- 若多格式适配器尚未就绪，先仅开放 docx 的完整审阅提交，其余格式继续停留在只读或预览态。

## Open Questions

- 搜索模式产生的回合是否要进入后续会话摘要与记忆模型，还是只作为检索历史保留？
- `ai-run-file-artifacts` 是否需要在本次 change 中显式区分 `preview`、`draft`、`committed` 三类产物，还是由新的审阅契约单独承载？
- PDF 的首个可交付语义应该是“批注/导出新文件”，还是“受限文本替换 + 导出新文件”？
