## Context

当前 AI 运行时已经形成 `Main Graph + Human Subgraph + Capability Registry` 的稳定边界，并且事件流契约集中在 `src/shared/types.ts`，具备良好的可测试基础。  
但仓库尚未建立面向 AI 架构效果的统一测试框架，缺少可复用的用例契约、可回放执行器、效果评估指标与标准化报告，导致后续能力迭代只能依赖人工验证，回归风险高且难以让 Codex 自动化扩展测试。

该变更属于跨模块设计：会涉及 `src/main/services/ai/**` 的可测试性注入点、测试目录组织、脚本入口与测试工件输出规范；同时需要保证不破坏现有运行时契约与进程边界。

## Goals / Non-Goals

**Goals:**
- 建立统一 AI 测试框架（harness），覆盖 `tool`、`human`、`context enrich`、`plan` 四类效果测试。
- 建立机器友好的场景 DSL 与夹具机制，支持后续由 Codex 自动生成用例并直接执行。
- 建立稳定断言层：契约断言、事件流断言、效果评分断言。
- 建立标准化结果产物（JSON + Markdown 摘要）与失败分类，为自动修复建议提供输入。
- 通过可控依赖注入，支持“默认确定性离线测试 + 可选真实模型回归测试”双模式。

**Non-Goals:**
- 不包含 Playwright 或 Renderer UI 自动化测试。
- 不重构现有 AI 业务能力实现逻辑（terminal/docx/retrieval 的业务行为保持不变）。
- 不引入云端评测平台或在线标注流程。
- 不改变既有 IPC 协议主语义，仅在需要时补充测试侧类型或工具。

## Decisions

### 决策 1：测试框架采用 Vitest（Node/Main 进程优先）
- 决策：
  - 使用 Vitest 作为统一测试运行器，优先覆盖 Main 进程 AI 架构测试。
  - 新增 `ai:test`、`ai:test:watch`、`ai:test:report` 等脚本入口。
- 选择原因：
  - 与现有 TypeScript + Vite 生态一致，启动和并发执行成本低。
  - 对 ESM/TS 兼容更顺滑，适合在本地快速迭代用例。
- 备选方案：
  - Jest。
  - 不采用原因：在当前工程中额外适配成本更高，且不具备明显收益。

### 决策 2：定义场景化 Case DSL，作为测试扩展唯一入口
- 决策：
  - 在 `tests/ai/cases/**` 使用 JSON 用例文件作为统一输入。
  - 用 zod 定义并校验 DSL schema，字段覆盖：`suite/input/setup/mocks/expects/score`。
  - 用例按 suite 组织：`tool`、`human`、`context`、`plan`。
- 选择原因：
  - JSON 结构稳定，便于 Codex 自动生成与程序化修改。
  - schema 校验可前置发现非法用例，避免执行期隐式失败。
- 备选方案：
  - YAML 或纯代码测试文件。
  - 不采用原因：YAML 容易出现语义歧义；纯代码用例不利于自动批量生成和治理。

### 决策 3：采用“适配器 + 断言器 + 报告器”三层测试架构
- 决策：
  - `adapters` 负责执行（tool/human/main-context/plan）。
  - `assertors` 负责校验（契约、事件轨迹、效果分数）。
  - `reporters` 负责产物（JSON、Markdown、退出码）。
- 选择原因：
  - 将“如何执行”和“如何判定”解耦，便于后续新增能力族测试。
  - 同一用例可复用不同断言策略，提升长期可维护性。
- 备选方案：
  - 在每个 suite 内部硬编码执行+断言。
  - 不采用原因：会导致重复实现，后续扩展成本高。

### 决策 4：引入可测试性注入点，替代对真实模型与随机性的硬依赖
- 决策：
  - 为模型调用与关键运行时依赖提供测试注入能力（如 scripted model、事件采集器、可控时间/ID）。
  - 默认测试走确定性 mock；可选 profile 走真实模型进行小规模回归。
- 选择原因：
  - 当前 human brain 直接调用模型工厂，难以稳定复现复杂步骤。
  - 不可控随机性会降低回归信号质量，影响自动修复判断。
- 备选方案：
  - 运行时 monkey patch 模型工厂。
  - 不采用原因：侵入性强、行为不透明，维护风险高。

### 决策 5：为四类测试定义统一通过标准与评分口径
- 决策：
  - Tool：校验输入输出契约、门禁语义、事件对完整性。
  - Human：校验步骤循环、失败分级、收敛动作与步数边界。
  - Context：A/B 比较补上下文前后在计划质量或任务成功率上的变化。
  - Plan：校验计划结构合法性、任务可执行性、执行事件顺序。
  - 引入分数阈值与失败分类（如 `tool_contract_error`、`context_effect_low`）。
- 选择原因：
  - 单纯 pass/fail 无法反映效果退化程度，不利于迭代优化。
  - 失败分类可直接驱动 Codex 生成修复建议。
- 备选方案：
  - 只做布尔断言。
  - 不采用原因：对效果评测支持不足，难以做趋势追踪。

### 决策 6：测试目录与工件目录独立，不污染运行时代码边界
- 决策：
  - 测试主资产放在 `tests/ai/**` 与 `artifacts/ai-test-results/**`。
  - 运行时仅新增必要的可测试接口，测试框架实现放在独立 testing 模块。
- 选择原因：
  - 符合项目目录规范，保持 Main/Renderer/Shared 主边界清晰。
  - 便于 CI 制品归档与本地排障。
- 备选方案：
  - 将测试实现散落到各业务目录。
  - 不采用原因：会放大耦合并降低可发现性。

### 决策 7：以文档规范 + Skill 触发约束统一测试执行入口
- 决策：
  - 在 `doc/` 下新增 AI 测试规范文档，作为测试框架、用例设计、结果判定的一致性依据。
  - 在 `.codex/skills/` 下新增对应测试 skill，要求 Codex 在处理 AI 测试相关任务时先读取测试规范文档。
- 选择原因：
  - 将“测试方法约束”从临时对话要求沉淀为稳定工程规则，减少执行漂移。
  - 让后续自动化生成测试与修复建议时具备统一前置上下文。
- 备选方案：
  - 仅在 AGENTS.md 增加一句说明，不增加 skill。
  - 不采用原因：触发条件不够强，后续自动化任务容易遗漏前置规范阅读。

## Risks / Trade-offs

- [可测试性注入点引入后影响生产路径] → 采用默认实现不变、测试注入显式启用的方式，并在 typecheck/lint 下确保契约一致。
- [事件顺序在异步场景下脆弱] → 使用“关键序列 + 关联字段”断言，不对非关键并发顺序做过度刚性校验。
- [过度依赖 mock 造成现实偏差] → 保留可选真实模型回归 profile，定期抽样验证关键场景。
- [Docx/Terminal 测试耗时较高] → 采用分层执行策略（smoke/full），默认本地运行 smoke，完整回归按需触发。
- [用例 DSL 演进导致历史用例失效] → 对 DSL 增加版本字段与迁移规则，保持向后兼容窗口。

## Migration Plan

1. 建立测试脚本与目录骨架，接入 Vitest 运行入口。
2. 实现 Case DSL 与 schema 校验，补齐基础 fixture 装载器。
3. 实现统一测试运行器（adapter/assertor/reporter）与结果产物结构。
4. 落地 tool suite（retrieval/terminal/docx）契约与事件测试。
5. 落地 human suite（循环行为、失败分级、收敛规则、步数保护）。
6. 落地 context suite（A/B 评测）与 plan suite（结构+执行效果）。
7. 接入失败分类与修复建议映射输出，形成 Codex 友好的诊断结果。
8. 在本地与 CI 验证 `lint/typecheck/ai:test` 全链路通过。

回滚策略：
- 若引入的可测试注入导致运行时不稳定，优先回滚注入点实现并保留测试目录资产。
- 若某类 suite 成本过高影响主流程，可先降级为可选 profile，保留框架主干与已稳定套件。
